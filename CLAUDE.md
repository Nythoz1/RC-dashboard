# CLAUDE.md — Rollin Coal Shop Management System

Guidance for Claude Code (and any agent) working on this repo. Read this fully before editing.

## Project overview

React + Vite single-page app for **Rollin Coal — Canada's Diesel Engine Specialists**, a diesel engine sales & service business in **Medicine Hat, Alberta**. Rollin Coal buys, remanufactures, and sells diesel engines Canada-wide, plus does HD service work.

- ~20 engines in live inventory (Caterpillar, Cummins, Detroit, International, Paccar, Mercedes, Mack, etc.) — the 80-row seed in `EMPTY` is only for fresh/local installs
- Phone 1-587-863-0505 · rollin-coal.ca · 2040 11th Ave NW, Medicine Hat, AB
- Brand: **Daylight** — light by default (warm off-white `#f3f2ef`, white cards, near-black text) with burnt orange (`#d4581a`) reserved for actions, the active nav item and alerts; a **Night** theme swaps the same tokens for dark surfaces. Public Sans (UI text) + Barlow Condensed (page titles, big numbers)

This was originally a Claude artifact (single `.jsx` using `window.storage` and a keyless Anthropic call). It has been converted to a real Vite project with a Supabase backend. **Do not reintroduce `window.storage`, `localStorage` directly in the component, `confirm()`, `alert()`, or a client-side API key.**

## Architecture of `RollinCoalDashboard.jsx`

Single file, intentionally. React with `useReducer`. Approximate map (search by the landmark strings, don't trust line numbers — they drift):

- `const FONTS` / `const EMPTY` — initial state, incl. 80-engine inventory seed + injector `parts` seed
- `const STORE_KEYS` — the persisted lists (see below)
- `function reducer` — actions: `TAB, MODAL, BACK, CLOSE, LOAD, ADD, UPDATE, DELETE, UNDO, TOAST, SPLASH, RESET`. `TAB` may carry `focus`, an engine id the Shop 3D view picks up. Modals keep a back stack in `mstack`: `MODAL` pushes the current modal (re-opening the same modal only refreshes `md`; opening one already in the stack unwinds to it; opening from no modal starts a fresh chain), `BACK` pops, `CLOSE`/`TAB` clear. The modal wrapper `W` shows a Back button when there is history (`W(ch, cls)`: `"rc-pmod"` = printable, `"rc-wmod"` = wide, used by the ECM job sheet). `ADD` closes the modal unless the action carries `keep:true` (used for uploads and settings saved from inside another modal). A toast with `long:true` stays 6.5 s instead of 2.2 s; the toast element is `role="status"` / `.rc-toast`.
- Helpers — `$$, $K, invTot, qTot, qTax` (through `Mny`: each invoice and quote carries its own `taxRate`), `stk, cn, sameId` (ids compared as text, so a link saved as text still resolves), engine helpers (`isEngine, engStatus, costBasis, trueMargin, marginPct, engLinks`), `CHANNELS`, `compressImg`
- `saveAll(s, keys, prev, role) / loadAll(role) / clearAll()` — call `db` from `lib/storage` with `"rc:"+k`. `keysFor(role)`: an employee login loads and saves only `EMP_KEYS` (`timesheets`, `payPeriods`); a login with no role gets none; every other list loads as `[]` and the research seed is skipped. `saveAll` returns `{failed, refused}`: lists that didn't reach the server, and rows the database turned down.
- **Saving (in `App`):** one save at a time through a promise queue (`saveQ`, `saveRef.current()`), each comparing the lists with `lastSaved` at the moment it runs, so an undo right after a delete still goes through. The 500 ms debounce feeds the queue. A failed save keeps its lists dirty and retries on a backoff timer (4 s doubling to 60 s), on `online` and when the app comes back to the front; `saveBadge` ("⚠ Not saved yet · retrying", `.rc-savebad`) sits in the header (and the employee header) until it lands, and `beforeunload` warns while anything is dirty. Refused rows go through `putBack`: those rows (and the pay periods, for timesheets) are reloaded and put back to what's saved, with `refusedMsg` saying why ("Couldn't save Sep 2: that pay period is approved"). `leave` (every Sign out) waits for pending saves; if it still can't save, a second tap within 10 s leaves anyway. Reset (`clearAll`) exists only in local mode; in the cloud it would wipe everyone's data and re-save the 80 demo engines. `loadAll` seeds `EMPTY` only for keys that were **never persisted**; a stored empty list stays empty (deleting every row no longer re-seeds it).
- Shared UI — `Badge, Stat, SH, Fil, Empty, Tbl, BtnRow`
- Views — `Overview, Customers, Quotes, Inv, Shop3D, Parts, Issues, Ecm, Invoicing, Operations, Marketing, Prospects, Competitors (+ ComparePanel), Services, Schedule, Emps (+ Timesheets), Reports`, plus `EmployeeShell` (+ `MyTimesheet`), the whole app for an employee login
- `function Modals` — every add/edit/detail modal; helpers `F, CS, ES, TS, PH, FM, EFM, LI, W, X, C`. Form prefill lives in one `useEffect` on `[s.modal]`: the generic reset runs **first** (`edit-*` copies `s.md` into the form; everything else starts from `s.md.prefill` + a few keys), then per-modal prefills merge on top with `sf(pp=>({...pp,…}))`. Keep that order — a plain `sf(obj)` after the merges wipes them. The effect lands one render after the modal opens, so a form that must be right on its first frame (like `sell-engine`) derives its defaults while rendering instead.
- `const CSS` — full stylesheet string injected via `<style>`
- `export default function App` — role (`app_metadata.role`: owner / staff / employee, anything else `"none"`, which gets a "doesn't have access yet" screen; local mode is the owner), load/save effects, theme, the shell (an employee login, or the owner's *See X's screen* preview, gets `EmployeeShell` instead) (sidebar `rc-side` + `rc-main` with the page header `rc-top`), tab routing, toast UI. `ICO`/`Ico` are the sidebar's inline SVG icons; `THEMES` the Day/Night/Auto switch

### State shape (`STORE_KEYS`, all arrays)
`customers, jobs, timeEntries, quotes, inventory, invoices, schedule, employees, expenses, leads, social, campaigns, contentCalendar, cores, shipments, commsLog, purchaseOrders, warranties, parts, wins, activity, settings, diagnoses, issues, brief, boms, bomSheets, vendors, services, ecmJobs, ecmFiles, prospects, competitors, compare, timesheets, payPeriods`

Transient state (NOT persisted): `tab, modal, md, mstack, focus, toast, lastDel, soldSplash`. `saveAll` only writes `STORE_KEYS`, so these never hit the DB. `brief` is the one `STORE_KEY` the app never mutates (server-written by the brief function), so it is never dirty and never saved by the client.

### Navigation
A left sidebar (`NAV` in `App`) lists every view, grouped: Overview · **Shop** (Engines, Shop 3D, BOM, Parts, Issues, ECM) · **Sales** (Marketing, Prospects, Competitors, Services, Quotes, Invoicing) · **Operations** (Customers & Jobs, Operations, Schedule) · **Business** (Team, Reports). The page title in `rc-top` comes from `TABL[s.tab]`. At ≤900px the sidebar becomes a slide-out drawer opened by the ☰ button (`navOpen`, `.rc-shell.nav-open`) and closes on navigation or a tap on the scrim. The sidebar footer holds the theme switch, the signed-in email, Backup, Reset and Sign out. Team has a **Team | Timesheets** switch (remembered per device as `rc:teamView`). An employee login has no sidebar: `EmployeeShell` is a header (name, Password, Sign out), their timesheet and the theme switch. Tab keys (`s.tab`: overview, inventory, shop3d, parts, boms, social, prospects, competitors, services, issues, ecm, customers, operations, schedule, quotes, invoices, employees, reports) are unchanged, so `TAB` dispatches still target individual views.

### Theme (Daylight + Night)
All colour comes from CSS custom properties on `.rc-root`: `--bg` page, `--sf`/`--sf2` surfaces, `--in` inputs, `--ln`/`--ln2` borders, `--tx`/`--tx2`/`--mt`/`--ft` text from strongest to faintest, `--ac`/`--act`/`--acs`/`--ach` accent (fill / text / soft background / hover), status pairs `--g/--gs` good, `--w/--ws` warn, `--r/--rs` bad, `--b/--bs` info, `--p/--ps` AI, plus `--sh1`/`--sh2` shadows and `--ov` modal scrim. The bare `.rc-root` block is Day; `.rc-root[data-theme="night"]` redefines the same tokens. `App` computes `theme` from the per-device preference `rc:theme` (`lib/prefs.js`: `day` default, `night`, or `auto` = follow the device's `prefers-color-scheme`) and stamps it on every root (`App`, `Login`, the splash and the load-error screen). Printing always uses Day tokens. The SOLD splash deliberately keeps its own dark backdrop in both themes. The printed engine sheet and the brief email are separate documents with their own fixed styling.

## Key domain concepts (important — this is an engine shop, not a parts store)

- **Engine unit record (the "passport").** Each engine in `inventory` with `cat==="Complete Engine"` (or `"Core"`) is a serialized unit. Fields: `serial`/`esn`, `cpl`, `arrangement`, `year`, `ratedHp`, `oilCap`, `sourceCore`, `status`, `photo`, `listedOn`, and a cost-basis breakdown (`costCore, costFreight, costParts, costLabor`). Opening an engine shows the full passport (in `Modals`, `s.modal==="part-detail"`), laid out as five tabs — Overview (identity, total-in/list/margin strip, lifecycle, notes) · Costs (cost basis + pricing, parts log, reman labor) · BOM (long block parts order + decision sheet) · Diagnosis (history + known issues) · Sell (channels, linked records) — with header/photo/underwater banner/actions always visible. Tab state is `ptab` in `Modals`; it persists across re-renders and Back for the same engine, and callers can land on a tab by passing `ptab` on the modal payload (e.g. `{...eng, ptab:"diagnosis"}`).
- **Lifecycle status** (`ENG_STATUSES`): `core → in-reman → available → on-hold → sold`. Use `engStatus(i)` (reads `i.status`; falls back to "available", or "core" for cores). Don't store status as free text in `notes`. Engine availability/stock derives from `status`, **never `qty`** — `qty`/`reorder`/`stk()` are parts-only. The **Reman Board** (Inventory tab → toggle, `view==="board"` in `Inv`) is a kanban of the five stages: drag a card or use ←/→ to set `status`, click a card to open its passport, and the header surfaces WIP capital (cost basis tied up in `core`/`in-reman`/`on-hold`). Reuses the `rc-bcol`/`rc-bh`/`rc-jc` board classes plus `rc-rboard` (5-col).
- **Shop 3D: the shop and yard in 3D, with every engine where it's kept** (Shop → Shop 3D, `Shop3D` view; replaced the 2D Yard map). The plan in `src/shop3d/areas.js` comes from the shop's floor plan sketch at about 4 px to the foot (Bay 1 ≈ 21 × 40 ft): 14 places (`SHOP_AREAS`: take-out inventory West and East, reman inventory, truck yard, parking, Bay 1, Reman 1 and 2, part cleaning, tools, parts inventory, office, lobby, bathroom). Engines can be kept in the seven `STORE_IDS` places, each with fixed spots (`SLOTS`: pallet rows with a forklift lane, the stand at each reman station, a strip beside the truck in Bay 1). **Where an engine is:** its own `loc` field (a storage place id) when set; otherwise `shopLocs` decides by lifecycle stage. In reman now: the Reman 1 stand, then Reman 2, then Bay 1. Went through reman in the shop (`remanned`: its `stageLog` passed `in-reman`, or its condition says reman / rebuilt / overhaul): reman inventory. Cores and runners: take-out, West until its spots fill, then East. Sold engines leave the map unless they have a `loc` (waiting for pickup; *Picked up* clears it). Engines past a place's spots aren't drawn but are listed on its card. `engLocs(s)` gives the whole map; the Engines list shows each engine's place (📍, searchable by place name) and the passport header has *📍 place · Show in 3D*, both via `TAB` + `focus`. Changing `loc` logs to the Shop Log. The view: toolbar (Day / Dusk / Night, walls Cutaway / Up / Down, Roofs, Labels, Tour, Overview, Drive the forklift with W A S D or the arrows, touch pad on phones), the stage, and a side panel (Places with counts → a place's card and its engines → an engine's card with *Where it's kept* and *Open passport*). `scene.js` loads on demand (three.js stays out of the main bundle), needs WebGL (shows a message without it), turns three's colour management off and outputs linear so the hex colours look as written, merges static props per place and material, rebuilds the engine meshes only when the engine list changes, declutters labels (selected and nearest first; a label that would overlap or hang off the edge hides) and disposes everything, context included, when you leave the tab. Engine paint comes from the make in the name; size from the family (`sizeClass`).
  - **The crew** (`src/shop3d/crew.js`, the *Crew* card above Places, the *Crew* toolbar toggle). Every Team member with `status:"active"` is a blocky figure at a work spot (`CREW_SPOTS`: the reman stands and benches, under the hood and in front of the truck in Bay 1, tools, the washer and hot tank, parts shelves, the two office desks (sitting), the lobby counter, a walk in the truck yard, two more on the Bay 1 floor). `crewList` keeps it stable (by id): the employee's own `station` when it's free (*Works at* on the person's card, an `UPDATE` on `employees`), otherwise the first free spot for their role (office, owner and IT at the desks / parts / apprentice and cleaning / yard keywords; mechanics and anyone else on the shop floor); more people than spots are listed, not drawn; people on leave stay home. A tech whose reman stand is empty works at the end of that bench (`alt`), so nobody wrenches on air. They work **8:00 AM to 4:00 PM, Monday to Friday, Medicine Hat time** (`shopClock`, `onShift`, the same `FULL_DAY` as timesheets) and aren't drawn outside it (the card says when they're back). Each hour that finishes (9:00 to 4:00, `hoursDone`), every working person's hourly rate (`employees.rate`) floats up over them (`api.pay`, `.s3-pay`), and the clock chip and the Crew card show *wages so far today* (`wagesSoFar`: rate × hours worked). **Money is owner-only** (`owner` = `ownerView`): staff and *Preview as staff* see the crew, the clock and the hours, never a rate, a total or a pop. **▶ Play the day** replays 8:00 to 4:00 in 48 seconds (`S3_SEC_H`), paying out each hour, ends on the day's total, then returns to live time. Figures: coveralls, cap and wrench on the shop floor, a shirt in the office; built from shared geometry, animated per kind of work (`crewStep`, still under reduced motion), with name tags that declutter with the other labels; picking one (3D, its tag, or the card) rings them and flies the camera there (from the north when they're in the yard).
- **True margin.** `costBasis(i)` sums the cost (see *Cost basis rule*); `trueMargin`/`marginPct` use it. A returned core can erase margin — keep cost basis honest.
- **Linked records.** Invoices, cores, warranties, shipments may carry `engineId` pointing at the inventory item. `engLinks(s, id)` resolves them (with `sameId`; the edit forms keep `…Id` fields as they are, and the customer and engine pickers store numbers); the passport renders them. The "Sell Engine" button in the passport opens the **Sell Engine** form (`sell-engine`, see *Services* below), which creates the invoice and flips the engine to `sold`.
- **Labor / time tracking.** `timeEntries` (`{id, jobId, tech, date, hours, rate, notes}`) logs labor against a work order, linked by `jobId` (a separate list, not embedded on the job). The Work Order modal (`job-detail`) shows logged time + hour/$ totals, with **Log Time** (→ `add-time`; the tech picker prefills `rate` from the employee). An entry's `rate` is what the tech is **paid**, so hours × rate is what the work **costs** the shop — never what the customer is charged (that's the job's charge, see *Services*). Reports rolls it up as *Labor by Technician* (hours + labour cost at tech pay). `rate` is snapshotted onto each entry so historical labor cost survives employee rate changes.
- **Services — what we did and what we charged.** `services` is the price list (Sales → Services, `Services` view), seeded from `servicesSeed.js`: `{id, cat, name, pricing:"flat"|"hourly", price, hours, desc, withEngine, preTick, active}`. Hourly services bill at `settings.shopRate` (the customer-facing labour rate, set on the Services page — separate from tech pay). `withEngine` services show in the Sell Engine form; `preTick` ticks them there by default; `active:false` hides one from pickers without losing its history. Work orders (`jobs`) now have a **kind** (`jobKind`): `reman` = labour into an engine we own — its time lands on that engine's cost basis (`syncLabor` only counts reman jobs), nobody is billed; `service` = work for a customer, charged on its own — its hours are that job's cost and **never** touch an engine's cost basis, even when it's linked to one (the swap that goes with a sale must not make the engine look less profitable). Jobs saved before `kind` existed: linked to an engine → reman, otherwise service. A service job carries `svcId`, `pricing`, `charge` (flat) or `rate` (hourly, defaults to the shop rate), and `invoiceId` once billed. `jobCharge` is what the customer pays: flat → `charge`; hourly → hours logged × rate until billed, then frozen at what the invoice said. `jobInv` is the only "is it billed?" check — it requires the invoice to still exist, so deleting that invoice un-bills the job and undo re-links it. Helpers: `jobTime/jobHours/jobCost` (cost at tech pay), `jobPricing`, `jobRate`, `jobBillLine`, `svcDefault`, `svcStats` (per service: jobs, charged, hours, cost; plus invoice lines added straight from the price list with no work order). The Work Order modal (`add-job`/`edit-job`, one form) picks the kind, customer, service and pricing; `job-detail` shows charged / labour cost / labour profit, billed status, and **Bill this job** (→ `add-inv` with `jobBillLine`). Invoice lines may carry `svcId` and `jobId`; creating an invoice stamps `invoiceId` + the billed `charge` on every job it bills. **Sell Engine** (`sell-engine`): customer (or a new one by name), engine price, a checklist of `withEngine` services with a charge each, truck/unit → one invoice (engine line `kind:"engine"` + one line per service) + a `service` work order per ticked service (`invoiceId` set, linked to the engine) → engine `sold` (so the warranty automation runs). The passport's Sell tab lists *Services with this engine* and the whole-deal total; Reports has a *Services* section (charged, labour cost, labour profit, engines sold with a service). `LI` (invoice and quote lines) has a price-list picker. Prices ship blank — the shop sets its own.
- **ECM programming jobs** (ECM tab, `Ecm` view; job sheet modal `ecm-job`, new-job form `add-ecm`, price list `ecm-prices`). Scope is parameter programming, factory calibration updates, ECM replacement/setup, injector trim codes, post-swap setup and emissions-intact tunes **only** (`ECM_TYPES`). **Hard rule: there is no "delete" job type and no field that records removing or disabling EGR / DPF / SCR. Don't add one.** `ecmJobs` record: `{id, date, status(intake/baseline/in-progress/verify/complete/on-hold), holdReason("emissions"|"manual"), holdFrom, completedAt, custId, unit, vin, year, make, model, family (a FAMILIES key, see ECM_FAMS), esn, cpl, arrangement, ecmPn, ecmSn, calCur, hp, tq, trans, transModel, axle, tire, gvw, application, terrain, odo, engHours, engineId (our inventory engine, optional), goals:[], goalNotes, emisIn:{egr|dpf|scr:{ok:"yes"|"no"|"", notes}}, bFaults:[{id,code,desc,count,last,state}], trims:[6], trip:{fuel(L/100 km),idle,avgSpd,topGear,fuelUsed,def}, dpf:{regens,regenEvery(km),lastRegen,soot}, dynoB/dynoA:{hp,hpRpm,tq,tqRpm,boost,egt}, types:[], params:[{id,name,old,new,why}], calOld, calNew, tune:{vendor,file,ver,job}, tool, tech, hours, rate (tech pay), parts:[{d,v}], billTo("customer"|"warranty"), priceOverride, priceReason, invoiceId, billed, aFaults:[], roadTest, emisOut:{…}, signName, signDate, signOk, aiReview, aiAt, fu:{30|60|90:{date,fuel,regenEvery,faults,comments}}, comeback, comebackNotes}`. Inputs store raw strings; compute with `+v`. The job sheet saves every field as it's typed (`UPDATE` per change, like BOM ticks).
  - **The emissions rule lives in the reducer** (`ecmGuard`, run on every `ADD`/`UPDATE` of `ecmJobs`, so no screen can bypass it): any `"no"` in `emisIn` or `emisOut` forces `status:"on-hold"`, `holdReason:"emissions"` (remembering `holdFrom`) and blocks every status change; when the last "no" becomes "yes" the job returns to `holdFrom` by itself. Moving to in-progress/verify/complete needs the intake check all "yes"; completing also needs the release check all "yes" plus `signName` + `signOk` (`ecmMissing`). A refused change reverts the status and toasts why. A manual hold (`holdReason:"manual"`) is released by hand.
  - **On completion** the reducer books 30/60/90-day follow-ups on the Schedule (`ecmFollowups`: appointments carrying `ecmJobId` + `fuDay`, never twice). Recording a follow-up fills `fu[n]` (its `date` marks it done); the Schedule list's service cell opens the appointment, and `appt-detail` has **Open ECM job** (lands on the Follow-up tab).
  - **Money:** `settings.ecmPrices` is the posted flat price per job type. `ecmService` = sum of the ticked types' prices, or `priceOverride` (billing needs a `priceReason`); parts bill on top. Hours × `rate` are the job's **cost** (labour profit = service − labour), never a charge, following the Services rule. `billTo:"warranty"` (only with one of our engines linked) means no charge and `syncLabor` folds the hours and parts into that engine (`laborLogged` / `dxParts`, so the Morning Brief's mirrored `costBasis` needs no change). Customer-paid ECM work never touches an engine's cost basis. **Bill this job** opens `add-inv` with `ecmBillLines` (lines carry `ecmJobId`); creating the invoice stamps `invoiceId` + `billed` on the job, and `ecmCharge` is then frozen at `billed`. `ecmInv` is the only "is it billed?" check (the invoice must still exist).
  - **Files:** `ecmFiles` rows `{id, jobId, path:"<jobId>/<name>", name, size, type, at}`; the bytes go through `lib/files.js` (private `ecm-files` bucket when signed in; IndexedDB locally), never into app_state or the JSON backup. CSV, TXT, XML, PDF, ZIP and images; 10 MB each. Names are kept unique per job before upload (upload uses `upsert`). Deleting a file is an undoable `DELETE`; the stored object is removed 12 s later only if the row didn't come back. Deleting a job keeps its files (so it can be undone); the ECM tab's storage card offers to remove files left from deleted jobs. Storage used is shown against the 1 GB free plan.
  - **AI review** (Verify tab) sends `ecmSummary` + up to 3 text logs (4,000 chars each) with `ECM_AI_RULES` as the system prompt **and** repeated in the message: explain and flag only, never calibration / fuel / timing / parameter values or anything that disables emissions equipment. AI errors toast instead of being saved.

## Conventions (follow these — they prevent regressions)

- IDs: `Date.now()`. Never sequential ints.
- Mutations go through the reducer (`ADD/UPDATE/DELETE`). Don't mutate state directly.
- Deletes are **undoable** via the toast (reducer stashes `lastDel`, `UNDO` restores). Don't add `confirm()`.
- Customer/tech/engine pickers are `<select>` dropdowns (`CS`, `TS`, `ES`), never raw ID text inputs.
- Date inputs: the `F` helper auto-renders `type="date"` for date-named keys (`DATEKEYS`). Defaults use `isoToday()`. `F(key, label, [[value, label], …])` renders a dropdown instead; every `F` label is tied to its field (`id="f-"+key`).
- A form's main button is never silently dead: grey it out and say why with `WHY(…)` (see the invoice form).
- Photos: `compressImg` (≤480px, JPEG q0.6) before storing; engines also accept an image URL.
- Type: UI text is Public Sans (`var(--fb)`), titles and big numbers Barlow Condensed (`var(--fd)`); numbers in tables use tabular figures. The scale was bumped once, globally (roughly +2px under 12px and +1.5px to 16px). Match the current sizes when adding UI — don't reintroduce 9–11px body text.
- Styling: add to the `CSS` string; reuse existing classes (`rc-card, rc-ba, rc-bs, rc-fi, rc-fg, rc-fl, rc-tn, rc-fb`...). **Never hard-code a colour in an inline style** — use the tokens (`color:"var(--mt)"`, `border:"1px solid var(--ln)"`), or both themes break. For a translucent fill or border of a status colour use `tint(c, pct)` (a `color-mix`), never a hex+alpha suffix like `col+"22"` — that stops working the moment `c` is a token. Only white text on the orange accent may be a literal (`#fff`). Print rules live in `@media print`.
- After edits, the build must pass: `npm run build`. Keep brackets balanced (the file is dense single-line JSX).

## Backend

- **Storage** (`lib/storage.js`): if `VITE_SUPABASE_*` set → Supabase. Else → localStorage. The component is unaware which; it just calls `db.getAll/getItem/setItem/removeItem`. `loadAll` uses `getAll`: every list in ~one round trip (one `IN(...)` query for the app_state blobs + one per table adapter, in parallel), and any failure marks the whole load untrusted (`__loadError`) instead of seeding over real data. Most lists are one JSON blob per key in `app_state`; lists that have graduated to a real table (see `TABLE_ADAPTERS`) route there instead — currently **`rc:inventory` → the `inventory` table**, **`rc:timesheets` → `timesheet_entries`** (text ids, `textId:true`) and **`rc:payPeriods` → `timesheet_approvals`** (per-row: a `data` jsonb the app reads verbatim + projected typed columns + a real `id` PK). Table reads page through 1,000 rows at a time (Supabase's response cap). When the database refuses a table upsert (`isRefusal`: 42501 row-level security, 23505 duplicate, 23514, P0001), each row is retried on its own and the refused ones come back as `{refused:[{id, code, message}]}`; deletes ask for the deleted ids back, so a delete row-level security filtered out is reported too. Anything else (no connection) throws, so the app retries. localStorage mode always uses the blob path (the cloud adapter is dead-code-eliminated when no Supabase env is set).
- **Applying migrations through the Supabase MCP:** `apply_migration` and `execute_sql` hold any statement containing `DROP` for a confirmation that a headless session can't give, so the call times out after 60 s and nothing runs. ALTER, CREATE OR REPLACE, REVOKE and upserts go straight through. On the live project, apply a DROP-free equivalent (plain CREATE for objects that don't exist yet, ALTER POLICY for ones that do), check its end state against the repo file in PGlite first, or run the file in the dashboard's SQL Editor. 0010 and 0011 went in that way on October 6, 2026.
- **AI** (`lib/ai.js` + `supabase/functions/ai`): `askClaude(prompt, { system })` POSTs to the Edge Function (`system`, optional and capped at 4,000 chars, is passed to Anthropic as the system prompt; a function deployed before that ignores it, so callers that depend on a rule also state it in the prompt), which calls Anthropic with the server-side key. Model via `ANTHROPIC_MODEL` secret (default `claude-sonnet-4-6`).

## Auth & security (implemented — P0)

Auth is wired up. When Supabase is configured the app requires an email/password login; on localStorage (no `.env`) it runs open for local dev — there is no shared backend to protect, so the gate is skipped.

- **Model: shared workspace.** `0002_auth.sql` replaces the old anon policy with one scoped to the `authenticated` role (`for all to authenticated using(true) with check(true)`). Any logged-in staff member reads/writes *all* shop data — no per-user isolation by design (it's one shop). 0011 narrows this for employee logins only (see *Roles*).
- **Invite-only.** Create users in Supabase Dashboard → Authentication → Users. Disable public sign-up (Authentication → Providers → Email → "Allow new users to sign up" OFF). There is deliberately **no sign-up form** — don't add one. Employees' logins come from the owner's Team tab (`team-logins`), never from a public form.
- **AI function requires a real user.** `functions/ai` verifies the caller's token with `auth.getUser()` and rejects the anon key (the anon key is itself a valid JWT, so gateway JWT-verification would let it through). Deploy it **with** `--no-verify-jwt` (`verify_jwt: false`): the in-function check is the real, stronger gate, and disabling the gateway check lets the browser's credential-less CORS preflight through.
- **The UI login gate is convenience only.** Real enforcement is server-side: RLS + the function's user check. A client that bypasses the React gate still can't touch data without a session.
- **Client:** `lib/auth.js` exposes `getSession/signIn/signOut/onAuthChange` and re-exports `usingCloud`. `App` renders `<Login>` when `usingCloud && !session`; the header shows the email + a Sign Out button. Load/save effects are gated on `authed`, so nothing reads or writes while logged out.

- **Roles (0011, 0013).** A login's role is its JWT `app_metadata.role`, which only an admin or the owner (through `team-logins`) can set; `user_metadata` is user-editable and never trusted. `"owner"`: everything; gives out logins and approves pay periods. `"staff"`: the whole dashboard, without wages. `"employee"` (plus `employeeId`, their Team member's id, and `name`): their own timesheet only. **No role: no access at all** (0013 allowlists roles; before it, any login that wasn't an employee counted as staff, so a login made straight in Supabase or an anonymous sign-in could read everything). SQL helpers: `public.is_owner()`, `is_staff()`, `is_employee()`, `my_employee_id()`, `shop_today()`, `ts_floor()`. The app_state, inventory and both storage bucket policies allow `is_owner() or is_staff()`. The timesheet tables let an employee read their own rows, add or change a day only from `ts_floor()` (the first of last month, mirrored by `Tsh.editFloor`) to today and not in an approved period (`ts_locked`, security invoker since 0012: it only ever checks the employee's own approvals, which they can read), and never delete one (0013; the app clears a day by saving it empty, so its history stays); approvals are unique per person and period; the owner writes any day up to today and is the only one who approves; staff read. The `ai` and `brief` functions turn employee logins away. In the app: `role`, `isOwner`, `isEmployee` (in `App`; local mode is the owner) and `keysFor(role)`. `preview` is `null`, `"staff"` (*Preview as staff*) or `{emp, name}` (*See X's screen*). `ownerView` (the owner, not previewing) goes to `Emps`, `Reports` and `Modals` as `owner` and hides the money from staff: timesheet pay, the Team table's Rate / Weekly / payroll stats, the employee Rate field and detail, the Log Time / Edit Time rate, Reports' Payroll/mo and *Labor by Technician* dollars, and the crew's rates, wage pops and totals in Shop 3D (`Shop3D` gets `owner`), the profit and loss's payroll and net, and the Overview's break-even (`Overview` gets `owner`; the brief keeps a staff copy without it). `Modals` also gets `who.role` (owner / staff / employee) for the day editor. **Still in shared data** every staff login can read: `employees.rate`, `timeEntries.rate`, ECM job `rate`, and job-level labour cost (work orders, the Services and ECM reports, engine cost basis). Moving those needs owner-only storage and touches labour costing.

Not yet done (future hardening): per-user audit columns, password policy. (Reset is local-only now.)

## Relational migration (in progress — incremental)

Goal: move each list from a single JSON blob in `app_state` into its own real table with enforced FKs (the engine↔invoice/core/warranty/shipment links are currently app-resolved by `engineId`, not DB-enforced).

**Pattern (per entity):** add a table with a `data` jsonb column (the exact object the app reads back — perfect round-trip, no reducer changes) + a few projected typed columns for SQL + a real `id` PK that child tables' FKs will reference. Add an entry to `TABLE_ADAPTERS` in `lib/storage.js` so the matching `rc:<list>` key routes to the table. Migrate the live data and retire the old blob (renamed to `rc:_bak:<list>_<nnnn>`). The dashboard/reducer don't change; the adapter syncs the whole list on each save (upsert + delete-missing).

**Done:** phase 1 — `inventory` (`0003_inventory_table.sql`). The timesheet days and approvals started out as tables (`0011_timesheets.sql`), same pattern. **Next, in order:** `customers`, then the linked cluster (`invoices, cores, warranties, shipments`) — once two linked entities are both tables, add the real `engine_id`/`customer_id` FK constraints. A later phase can refactor the reducer to true per-row async writes for efficiency/concurrency. Not required for the app to function.

## Safe-change checklist

1. `npm run dev` and reproduce the area you're changing.
2. Make the change; keep to existing patterns above.
3. `npm run build` must succeed.
4. Verify persistence (reload), and undo/toast still work for any list you touched.
5. If you added a `STORE_KEY`, add it to `STORE_KEYS`, `EMPTY`, and the save-effect dependency array in `App`. If the list affects an engine's cost, add it to `LABOR_LISTS` and fold it in `syncLabor`.
6. Printable modals (long block parts order, machine shop list) pass `"rc-pmod"` as the second argument to `W`; the print stylesheet re-shows that overlay only.
7. `npm test` runs the unit tests (`node --test`): hours, overtime, the access rule and history (`tests/timesheet.test.mjs`); the crew's spots, the 8-to-4 day in Medicine Hat and the hourly payouts (`tests/crew.test.mjs`); tax by province, due dates and aging, expense frequency, the profit and loss and break-even (`tests/money.test.mjs`); the Morning Brief's money and its staff copy (`tests/brief.test.mjs`, failing against the old brief); the 0011–0013 rules in a real Postgres (`tests/policies.test.mjs`, PGlite via `tests/fixtures/pg.mjs`, which applies the repo's migrations); the storage layer as a signed-in device (`tests/storage.test.mjs`: a table past 1,000 rows, a refused row or delete, a dropped connection); the team-logins function and the ai / brief role checks, run in Node against the PGlite-backed mock Supabase.
